# publish の学び

## 2026-09-05 production completion boundary

- 事象: 制作途中で別アカウントへ切り替わり、複数の販売者IDと登録先がある状態で誤入力する危険が生じた。また審査リクエスト後の追跡まで制作フローに含まれていた
- 原因: P8の前提にアカウント同一性がなく、制作の完了境界が外部審査状態へ依存していた
- 対処: P8開始時に画面のアカウント名、販売者ID、登録先をユーザーへ表示し、承認後にSESSIONへ記録する。入力直前にも再照合し、登録入力とプレビュー確認後は `production-complete` として定型文を表示する
- 再発防止: 審査リクエスト、追跡、リリースをゲートと状態から除外する。アカウント未確認・不一致では入力を開始せず、パスワードや認証コードを保存しない

## 2026-09-05 optional supporting evidence

- 事象: `license_proof` を常に必須メタへ含めると、追加資料を求められていない通常申請でも不要な確認が発生する
- 原因: 外部審査から個別に要求される可能性がある資料と、毎回確定すべき申請設定を同じ必須契約へ入れていた
- 対処: schema v3 のメタ例から `license_proof` を外し、欠落を正常とした。LINE から要求されユーザーが提示した場合だけ、任意の参照形式を検証する。旧形式の空の既定値は migration で削除し、提示済み資料は保持する
- 再発防止: 外部サービスが条件付きで要求する項目は通常フローの必須質問にせず、「欠落可・存在時は厳格検証」にする。法的同意や証跡の内容をエージェントが推測・作成しない

## 2026-09-03 registration declarations

- 事象: 申請メタが販売地域を2択として扱い、AI・写真使用やプレミアム参加を文字列または推測値で持つと、現行画面の選択内容を正確に再現できない
- 原因: 公開画面の法的同意、申告、参加設定と、作品メタを一つの曖昧な公開可否へまとめていた
- 対処: 販売エリアを `all|some|selected` と国コード一覧へ分離し、`ai_used`、`photo_used`、`premium_participation` を真偽値にした。当時はライセンス確認を `license_proof` として明示したが、現行 schema v3 では条件付きの任意情報である。「同意します」と審査リクエストはユーザー本人だけが行う
- 再発防止: P6/P8で公式画面・ガイドラインを再確認し、画面値を推測しない。`check-publish-ready` は `publish: yes` のP7候補だけに使い、法的有効性を保証する表現を避ける。仕様差分はこのファイルと `references/line-specs.md` の両方へ記録する
