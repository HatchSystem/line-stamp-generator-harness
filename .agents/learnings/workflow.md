# workflow の学び

## 2026-09-05 cross-platform CI fixtures

- 事象: Windowsでは解決済みパスと未解決パスの表記差で自己診断が失敗し、Ubuntuでは空マスクを比較用fixtureにしたため、製品側の正しい入力拒否で穴検査へ到達しなかった。macOSはCI対象外で、同種のパス差を検出できなかった
- 原因: テストの期待値を実装と同じ正規形へ揃えず、厳格化した入力契約を満たさないfixtureを正常系に使っていた。CIもOSとPython版の直積だけで考え、検査責務を分けていなかった
- 対処: パス期待値も `resolve()` し、正常系には穴を覆わない非空の有効マスクを使い、空マスク拒否は独立した異常系へ分けた。全品質検査はUbuntu + 最低Python版の1件、公開Python CLIは最新Python版のUbuntu・Windows・macOSで検査する
- 再発防止: 新しいバリデーションには、有効な正常fixtureと無効入力の拒否fixtureを別々に置く。CIは静的検査を1回だけ実行し、最低言語版と最新言語版、主要OS差を必要最小限の組み合わせで網羅し、同じrefの古い実行をキャンセルする

## 2026-09-05 versioned design contract

- 事象: 髪形、参考画像、背景、頭身などが三面図後に変わり、複数のデザインシートと三面図が混在した
- 原因: P1の承認が文章上だけで、数値・画像・参照元と下流成果物を同じ版へ結び付けていなかった
- 対処: P1で必須チェックリスト、数値の頭身、HEX配色、背景透過、画像と参考画像のハッシュを版付き証跡へ固定し、P2もその証跡のハッシュへ結び付ける。P1変更時はP2以降の状態を未承認へ戻す
- 再発防止: 下流の成果物コマンドは現在のP1/P2証跡を必須にし、ファイル差し替えや古い版との組み合わせを拒否する

## 2026-09-05 project learning promotion

- 事象: 制作中の問題が会話だけに残ると、次回の改善依頼で原因と対処を再構成できない
- 原因: 個別案件の観察記録と、Git管理する共有知見の昇格手順がなかった
- 対処: 各新規プロジェクトに追記専用 `LEARNINGS.md` を作り、問題・教訓、Phase、影響、原因、対処、改善候補を記録する公開コマンドを追加した
- 再発防止: 改善依頼ではプロジェクト記録と共有知見を先に読み、改善案を提示して承認後だけハーネスを変更する。秘密情報・個人情報は記録せず、再利用価値のある項目だけ共有領域へ昇格する

## 2026-09-05 historical figure exception

- 事象: 権利確認項目を P0 から廃止しても「著名人の似顔絵を受けない」という一律ルールが残ると、歴史上の人物も受付拒否の対象になる
- 原因: 対話上の確認省略と、題材別の受付可否を別々に変更していた
- 対処: ユーザーが歴史上の人物を題材とすると明示した案件は、著作権・肖像権・パブリシティ権・本人許諾・ライセンス証明の確認対象外とし、著名人を理由に拒否しない。SESSION schema や CLI 引数は増やさない
- 再発防止: 受付例外は AGENTS、スキル、対話、素材ルール、入力種別資料、利用説明へ同時に反映し、構成検査で固定する。内部チェックの除外と LINE 公式審査は分離し、LINE画面自体が追加資料を求めた場合は内部確認を再導入せず、表示内容をユーザーへ報告して停止する

## 2026-09-06 question timing boundary

- 事象: 作業中に質問UIが表示されるという報告に対し、一律禁止案を出したが、ユーザーは「必ず作業の区切り後に行う」ことを指定した
- 原因: 質問UIの可否と質問する時点を混同していた。発生時のログがないため、クライアント不具合の原因は断定していない
- 対処: 当該作業の処理を完了または安全に停止して途中結果を保存し、メインが区切り後にだけ質問する。回答まで次の作業を始めない。利用できない環境・モードでは通常チャットで質問する
- 再発防止: ツールの一律禁止に置き換えず、利用時点・回答待ち・利用不可時の応答方法を同時に定義し、共通ルールと製品アダプタを構成検査する。クライアント内部の実行状態を見ない静的フックで「区切り」を判定したと主張しない

## 2026-09-06 chat dialogue contract

同日の追加指示で、質問UIの一律禁止は「作業の区切り後だけ使用」へ変更された。以下は先行変更の記録。通常チャットは引き続き使え、明示的なゲート承認と状態記録も維持する。

- 事象: 質問ツールの指定を製品アダプタだけから削除しても、共通手順や構成検査が構造化UIを要求し続ける
- 原因: 対話形式の契約が複数の参照元と検証条件にまたがっていた
- 対処: ユーザー承認に基づき、質問・承認を通常チャットへ統一し、正本・製品アダプタ・構成検査を同時に更新した
- 再発防止: 対話形式変更ではツール名の使用指示だけでなく、同等UIへの誘導、フォールバック規定、承認テンプレートも確認する。明示的なゲート承認と状態記録は維持する

## 2026-09-05 structured intake contract

構造化選択UIの使用方針は2026-09-06の通常チャット方式へ変更された。以下は当時の経緯であり、共通正本と製品アダプタの分離、SESSION変更時の移行方針は引き続き有効。

- 事象: 共通手順へ製品固有の質問ツール名を直接書くと他環境で実行不能になり、受付項目だけを文書から消すと CLI・SESSION・公開前検査に旧契約が残る
- 原因: 対話能力の契約と製品別の実装方法、状態 schema と移行処理を別々に更新していた
- 対処: 共通層は「有限選択には構造化選択 UI」という能力契約にし、Claude アダプタだけに `AskUserQuestion` を明記した。P0 から `adult`、`consent`、`rights` を除き、schema v3 の dry-run 既定 migration で旧フィールドを削除するよう揃えた
- 再発防止: 受付項目を増減するときは、対話、CLI 引数、新規テンプレート、SESSION 契約、公開前検査、migration、fixture、製品アダプタの順に影響を確認する。製品固有名が共通層へ混入していないことを構造検査で固定する

## 2026-09-03 P0 state transition

- 事象: 新規案件の作成と P0 回答の確定が同じ操作に混在すると、素材配置前や回答矛盾がある状態でも P1 相当のセッションを作れてしまう
- 原因: 隔離先を先に用意する操作と、権利・許諾を含む受付ゲートの承認操作を区別していなかった
- 対処: `project new` は不完全な `gate: P0` だけを作り、素材をその `refs/` に置いた後、全回答を明示する `project confirm-p0` が一括検証・保存して初めて P1 へ進めるようにした
- 再発防止: ゲート遷移は専用コマンドへ集約し、必須回答の欠落・矛盾時に SESSION が一字も変わらないテストを置く。`adult`、`consent`、`rights` は後の schema v3 で廃止されたため、現行 P0 の契約には含めない

## 2026-09-03 project schema migration

- 事象: SESSION の `publish` 列挙値と申請メタの販売設定を明確化した結果、旧形式の案件は新しい公開前検査をそのまま通せなくなった
- 原因: 永続ファイルに schema version がなく、仕様変更と既存案件の意味保存変換を別々に扱っていた
- 対処: バージョンなしを v1、当時の現行を v2 と定義した。選択中案件だけを対象に、既定は dry-run、明示した `--apply` だけがバックアップ後に同一 filesystem 上で原子的に置換する移行コマンドを追加した。現行は同じ方式で v3 へ更新している
- 再発防止: SESSION や申請メタの必須項目・列挙値を変える変更には、新規テンプレート、互換移行、旧 fixture、冪等性、矛盾時の全停止を同じ変更セットで含める。移行でゲートや承認状態を進めない

## 2026-09-03 multi-agent source of truth

- 事象: ワークフロー、検証スクリプト、ルール、学びの大半が特定製品の設定ディレクトリにあり、他のエージェントから使う説明と実在パスがずれていた
- 原因: Claude Code の自動検出場所を共有資産の正本としても使い、製品別の発見方法とベンダー中立な内容を分離していなかった
- 対処: `AGENTS.md` と `.agents/` を共通正本、各製品の設定ディレクトリを薄いアダプタに分離し、公開 CLI を `scripts/line_stamp.py` へ固定した
- 再発防止: 共通層から製品固有層への参照、skill の重複、役割集合のずれ、壊れた相対リンクを `node scripts/check_structure.mjs` で検査する。新しい環境は正本を複製せず、発見できない差分だけをアダプタにする

## 2026-09-03 Windows runtime discovery

- 事象: Windows 環境で `python` と `bash` を PATH 経由で実行できず、初回の検証コマンドが失敗した
- 原因: Python は未導入で、Git Bash はインストール済みだが PATH に登録されていなかった
- 対処: Git Bash を `C:\Program Files\Git\bin\bash.exe` の絶対パスで呼び、参照整合性と Shell 構文を検証した。Python のセルフテストは未実行として明記した。Claude の旧Python hookはNodeランナーが `python3` / `python` / `py` を選び、すべて不在なら同じ共通Node hookへフォールバックするようにした
- 再発防止: Windows では検証前に `Get-Command` でランタイムを確認する。Git Bash は既知の絶対パスへフォールバックし、Python がなければ勝手にインストールせず確認を取る。安全hookの起動コマンドを単一のPythonコマンド名へ固定しない

## 2026-09-01 brace expansion

- 事象: 製品固有の設定ディレクトリを `mkdir -p <adapter>/{hooks,rules,...}` で作ろうとした際、`/bin/sh` でブレースが展開されず、波括弧を含む名前のディレクトリが作られた。続く `cd` が失敗し、設定ファイルがカレントディレクトリ（/）に書かれた
- 原因: 実行シェルが bash ではなく sh だった
- 対処: ディレクトリを個別に列挙して作成し、誤配置ファイルを移動
- 再発防止: 複数ディレクトリ作成はブレースを使わず明示列挙する。ファイル生成前に `pwd` と `ls` で場所を確認する
